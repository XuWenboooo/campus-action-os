# API contract

Every response includes `x-request-id`. Errors use `{ "error": { "code", "message", "requestId", "retryable" } }`. State-changing POST, PATCH and DELETE operations, including development login, profile updates and document deletion, require `Idempotency-Key`; a replay returns the original response, while reuse with a different request is a `409 IDEMPOTENCY_CONFLICT` (parse jobs persist an internal request hash for the same guarantee). Write routes reject unknown JSON fields instead of silently dropping them. Profile updates also append a `profile.updated` audit event. Soft-deleting a document, confirming/rejecting an action, completing or cancelling a task, publishing/revoking/postponing a notice, linking a notice to a task, and resolving a notice-task sync event all require an explicit confirmation body. Notice creation additionally requires publisher/admin role; only local development login may explicitly provision that role, and development login is disabled in `APP_ENV=production`.

The executable route surface is implemented in `services/api/src/server.ts`; the core proof covers login/profile, profile export, document creation/upload/read/delete, parse jobs, actions, tasks, notices, notice-task synchronization and feedback. `GET /users/me/export` returns a schema-validated `user-data-export/v1` object for the authenticated local user, including original text and integrity-checked media bytes; it does not expose another user's rows or provider credentials. `/documents/upload` accepts bounded canonical Base64 for `image/png`, `image/jpeg`, and `application/pdf`, stores it transactionally in SQLite, and can be parsed through the local offline extractor/OCR path or an explicitly injected OCR boundary. When parsing fails, `POST /tasks/manual` lets the current user explicitly confirm a user-authored title and optional due time; it records a manual action, user-input evidence and an audit event without claiming that OCR or fact extraction succeeded. `POST /tasks/:taskId/notices` links a confirmed Task to the latest published revision. Later published, postponed or revoked revisions appear at `GET /tasks/:taskId/notice-sync` as `pending_review`; `POST /tasks/:taskId/notice-sync/:syncEventId/resolve` records the user's accept/reject decision. Accepting a revocation cancels only a pending or in-progress Task.

The API also requires parser response `request_id` and `document_id` to round-trip to the API request before any action is persisted. A confirmed action may produce at most one pending/in-progress Task; completed, expired, cancelled, or rejected actions cannot be revived into a new Task, and SQLite enforces the active-task uniqueness invariant.
