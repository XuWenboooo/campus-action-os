## 0. 冻结规则

本文件冻结项目的科学问题、产品边界、数据划分、主要指标、成功阈值、程序目标和结果报告方式。冻结后不得因为实验结果不理想而修改主要指标、测试集、阈值或对照组。

允许修改的内容仅包括：修复实现错误、提升运行稳定性、改善交互和补充不影响主要结论的探索性功能。所有修改必须记录时间、原因、修改前后内容及是否查看过测试结果。

如果确需修改冻结内容，必须创建新的修订版，不得覆盖 v1.0；修订版必须注明：

1. 修改发生在查看测试结果之前还是之后；
2. 修改是否受已观察结果影响；
3. 原方案结果是否仍完整保留；
4. 新结果是正式验证还是探索性结果。

禁止行为：反复更换测试样本直到指标变好、删除失败案例、只展示最好模型、用测试集调整 Prompt、将人工修正后的输出记为模型自动结果、把内部演示账号包装成真实用户。

## 1. 项目总目标

### 1.1 产品目标

开发并上线一套面向高校学生和通知发布者的微信小程序，将微信群、截图、PDF、网页和附件中的非结构化校园通知，可靠地转换为：

- 与当前用户是否相关；
- 用户需要完成的一个或多个行动；
- 每个行动的截止时间、地点、平台、材料与前置条件；
- 每个结论对应的原文证据；
- 不确定、冲突或缺失信息；
- 可保存、提醒、更新和追踪的任务。

系统最终定位不是“AI 通知摘要器”，而是：

> **可信校园行动操作系统：将校园信息编译成可执行、可核验、可协同的行动。**

### 1.2 竞赛目标

同时构建两条竞争路径：

- **综合一等奖路径**：实用性、创新性、用户体验和作品完整度均达到可持续使用水平；
- **优秀 AI 作品路径**：证明 AI 在复杂通知解析和可靠行动生成中不可替代，并显著优于通用大模型直接问答。

奖金不是可保证的实验结果。项目内部以“一等奖标准完成作品”为目标，不以任何奖项承诺替代工程和实验证据。

## 2. 核心科学问题与冻结假设

### 2.1 核心科学问题

在存在 OCR 噪声、多人群条件、多阶段任务、日期歧义、附件依赖和通知变更的真实校园通知中，能否比通用大模型更可靠地生成个性化、可核验、可执行的行动？

### 2.2 主要假设

**H1：行动完整性。** Campus Action OS 的 Action Recall 显著高于“通用大模型 + 单次 Prompt”。

**H2：关键可靠性。** 系统的 Critical Error Rate 显著低于“通用大模型 + 单次 Prompt”。

**H3：证据可信度。** 字段级证据绑定能提高 Evidence Coverage，并减少无原文支持的关键断言。

**H4：个性化相关性。** 用户画像与适用对象匹配能提高 Relevance Accuracy，尤其能减少“无关通知被错误转成待办”。

**H5：用户效率。** 与人工阅读原通知相比，系统能降低理解与建任务耗时，同时不增加严重遗漏。

**H6：实际行动效果。** 在真实试点中，使用系统的学生任务按时完成率高于原有微信群通知流程。

### 2.3 探索性问题

- 多模型交叉复核相对单模型规则校验的收益；
- 发布端机器可读通知对学生端错误率的改善；
- 不同通知类别、长度和 OCR 质量下的性能差异；
- 提醒策略对完成率和打扰感的影响；
- 通知变更自动同步对错误任务的减少程度。

探索性结果不得替代主要假设结果。

## 3. 冻结产品边界

### 3.1 正式范围

仅覆盖高校校园事务：教务、学工、奖助、考试、竞赛、社团、就业、宿舍与校园公共服务。

正式输入：

- 粘贴文字；
- 单张或长截图；
- PDF/附件；
- 通知链接；
- 发布端生成的机器可读通知卡或二维码。

正式输出：

- 通知标题与类型；
- 适用对象与个体相关性；
- Action Graph；
- 截止时间及时间精度；
- 地点、平台、入口；
- 材料清单；
- 条件、例外和任务依赖；
- 后果与强制程度；
- 字段级证据及置信状态；
- 待办、提醒、变更和完成状态。

### 3.2 明确排除

- 医疗、银行、政务和企业办公泛化；
- 万能聊天机器人；
- 自动替用户完成缴费、报名或提交材料；
- 无法得到用户明确授权的消息推送；
- 高风险决定的全自动执行；
- 与核心闭环无关的虚拟人、社交广场和装饰性 AIGC。

## 4. 核心数据结构：Verified Action Object

每个行动对象必须包含：

```text
action_id
document_id
title
target_population[]
user_relevance: relevant | irrelevant | uncertain
relevance_reason
action_type
steps[]
dependencies[]
conditions[]
exceptions[]
deadline:
  value
  precision: minute | hour | day | range | unknown
  boundary_semantics: before | no_later_than | on | after | unknown
location
platform
entry_link
required_materials[]
consequence
obligation: mandatory | recommended | informational | unknown
evidence[]:
  source_text
  page_or_image
  bounding_box
  field_name
confidence
epistemic_status: explicit | rule_inferred | ai_estimated | unknown
verification_status: passed | conflict | user_confirmation_required
task_status: pending | in_progress | completed | expired | cancelled
change_history[]
```

关键字段为：用户相关性、行动步骤、截止时间、材料、地点/平台、条件与例外。关键字段没有证据时，不得显示为“原文明确”。

## 5. CampusActionBench 冻结方案

### 5.1 数据规模

总计 **800 条**匿名化真实或经合规重构的校园通知：

- 训练/开发集：480 条；
- 验证集：160 条；
- 冻结测试集：160 条。

最终测试集在第一次正式评测前生成 SHA-256 清单并只读冻结。正式模型、Prompt、规则和阈值只能依据训练/开发集与验证集调整。

### 5.2 覆盖要求

整个数据集至少满足：

- 30% 为多行动通知；
- 25% 包含两类及以上适用人群或排除条件；
- 20% 对给定用户画像无关；
- 15% 包含多阶段截止或任务依赖；
- 15% 包含附件/材料要求；
- 10% 包含日期歧义、内部冲突或信息缺失；
- 20% 为截图/PDF OCR 输入；
- 10% 为低质量截图、复杂排版或跨页输入；
- 10% 为通知变更、补充或撤销场景。

类别分布应覆盖教务、学工、奖助、考试、竞赛、社团、就业、宿舍和公共服务，任何单一类别不得超过总数据的 25%。

### 5.3 标注流程

每条样本由两名标注员独立标注，一名仲裁员处理不一致。标注内容包括：

- 适用对象；
- 给定画像相关性；
- 全部行动及先后关系；
- 时间及边界语义；
- 地点、平台、入口和材料；
- 条件、例外、后果与强制程度；
- 每个字段的原文证据；
- 无法确定的信息；
- 可能造成误办或漏办的关键字段。

在标注 80 条试运行集后计算一致性。分类字段 Cohen's kappa 目标不低于 0.80；跨度字段采用 token-level F1，目标不低于 0.90。未达标时先修订标注指南，再正式标注。

### 5.4 数据治理

- 删除姓名、学号、手机号、身份证号、具体住址等个人信息；
- 不保存未经许可的群成员信息；
- 对敏感材料截图做不可逆脱敏；
- 保存来源类别和授权状态，不在公开材料中泄露原通知隐私；
- 合成或重构样本必须单独标记，不得伪装成真实通知。

## 6. 冻结对照系统

**B0：人工阅读。** 用户阅读原通知并手动创建待办。

**B1：通用大模型单次 Prompt。** 输入相同 OCR 文本和用户画像，要求直接输出摘要与行动；不使用系统规则、证据校验或二次复核。

**B2：结构化 Prompt。** 使用固定 JSON Schema，但无字段级证据验证、Action Graph 校验和严重错误盾。

**S0：完整系统。** 文档理解 + 结构化抽取 + 身份匹配 + Action Graph + 字段证据 + 规则校验 + 风险复核 + 置信校准。

消融系统：

- S0-E：去除字段级证据验证；
- S0-R：去除身份匹配；
- S0-G：去除 Action Graph，只生成扁平任务；
- S0-C：去除严重错误盾；
- S0-V：去除多阶段一致性复核。

所有系统使用固定版本的模型、Prompt、温度、OCR 和依赖。正式测试期间禁止自动升级模型。

## 7. 冻结评价指标

### 7.1 主要指标

1. **Critical Error Rate（CER）**：出现至少一个会导致用户误办、漏办或错过截止的严重错误的样本比例。
2. **Action Recall**：标准答案中的必要行动被正确提取的比例。
3. **Deadline Exact Match**：日期、时刻、范围及“之前/截至/当天”等边界语义完全正确的比例。
4. **Relevance Accuracy**：系统对给定用户画像是否相关的判断准确率。
5. **Unsupported Critical Claim Rate**：无原文证据却被系统作为确定事实输出的关键断言比例。

### 7.2 次要指标

- Action Precision 和 Action F1；
- Material F1；
- Condition/Exception F1；
- Evidence Coverage；
- Evidence Span F1；
- Expected Calibration Error；
- 解析成功率、P50/P95 延迟、失败恢复率；
- 用户完成理解所需时间；
- 用户纠错次数；
- 任务按时完成率；
- D1/D7 留存、周活跃用户和每周保存任务数。

### 7.3 冻结成功阈值

完整系统 S0 必须同时达到：

| 指标 | 最低通过线 | 冲一等奖目标 |
|---|---:|---:|
| Critical Error Rate | ≤ 2.0% | ≤ 1.0% |
| Action Recall | ≥ 92% | ≥ 95% |
| Deadline Exact Match | ≥ 95% | ≥ 97% |
| Relevance Accuracy | ≥ 96% | ≥ 98% |
| Unsupported Critical Claim Rate | ≤ 1.0% | ≤ 0.5% |
| Evidence Coverage | ≥ 95% | ≥ 98% |
| 自动解析成功率 | ≥ 97% | ≥ 99% |
| P95 端到端延迟 | ≤ 15 秒 | ≤ 8 秒 |

“达到一等奖目标”仅指达到本项目内部质量门槛，不代表赛事结果保证。

## 8. 正式实验矩阵

### E1：离线主对照实验

- 数据：冻结测试集 160 条；
- 系统：B1、B2、S0；
- 主要终点：CER、Action Recall；
- 次要终点：Deadline Exact Match、Relevance Accuracy、Unsupported Critical Claim Rate、Evidence Coverage；
- 每条样本固定输入和用户画像；
- 失败和拒答全部计入，不得删除。

### E2：消融实验

- 数据：同一冻结测试集；
- 系统：S0、S0-E、S0-R、S0-G、S0-C、S0-V；
- 目标：证明每个核心模块确有贡献；
- 报告整体结果及复杂通知、OCR、负相关、歧义日期四个子集结果。

### E3：鲁棒性实验

在不改变语义的前提下，对测试输入施加：压缩、裁剪、模糊、错别字、段落乱序、跨页拆分、OCR 字符替换。报告不同扰动等级下的性能曲线和失败模式。

### E4：时间边界专项实验

构建 100 个独立时间表达测试用例，覆盖“前”“之前”“截至”“当天”“工作日”“报名开放区间”“补交”“延期”和互相冲突的日期。该集合仅验证时间解析器，不与主测试集混合。

### E5：用户效率随机对照实验

- 计划样本：至少 60 名高校学生；
- 随机分配顺序：人工阅读流程与系统辅助流程交叉进行；
- 每位参与者处理 4 条通知，其中 2 条复杂通知；
- 主要终点：正确建立全部任务所需时间、严重漏项率；
- 次要终点：NASA-TLX 简化认知负担、信任度、证据点击率；
- 记录用户最终确认后的结果，同时保留 AI 首次输出结果，两者不得混淆。

### E6：真实校园试点

- 至少 3 个独立组织，优先为不同类型：班级/学院、社团、竞赛或实验室；
- 连续运行至少 14 天；
- 累计不少于 100 名真实用户、300 次真实通知解析、500 个生成任务；
- 指标：激活率、周活、任务保存率、提醒授权率、任务完成率、错误报告率、通知发布者节省时间；
- 如未达到样本量，必须如实报告，不得按百分比制造规模感。

### E7：现场演示压力测试

固定 5 条此前未用于开发的复杂通知，连续现场运行 20 次。要求：

- 零崩溃；
- 全部关键字段正确或明确触发确认；
- 网络故障时能提示并进入备用流程；
- 演示数据、真实数据与预置样例清晰标注。

## 9. 统计与结果报告规则

- 所有比例指标报告点估计和 95% bootstrap 置信区间；
- B1/B2 与 S0 的配对二分类结果使用 McNemar 检验；
- 连续耗时优先报告中位数、四分位距，并使用配对非参数检验；
- 多重次要比较使用 Holm 校正；
- 显著性水平为 0.05，但不得以显著性代替实际效应大小；
- 主结果按完整测试集报告，同时报告复杂通知、OCR、无关通知、歧义时间子集；
- 拒答、超时、解析失败均保留在分母中；
- 人工纠错前和纠错后性能分开报告；
- 正式结果表必须列出所有基线与所有消融，不只展示最优项；
- 建立错误案例册，至少展示 10 个成功案例和全部严重失败案例。

## 10. 程序总目标

### 10.1 学生端目标

1. 微信登录与最小化用户画像；
2. 文字、截图、PDF、链接和附件导入；
3. 复杂通知解析；
4. “与我相关/无关/无法确定”判断及解释；
5. 多行动、条件分支和依赖关系展示；
6. 字段点击回到原文证据位置；
7. 不确定与冲突字段的用户确认；
8. 行动卡保存、编辑、完成和取消；
9. 材料清单与完成勾选；
10. 在微信授权范围内创建订阅提醒；
11. 通知变更、延期和撤销同步；
12. 任务中心：今天、即将截止、等待前置、已完成；
13. 原始内容与个人数据删除/导出；
14. 错误反馈和证据纠正入口。

### 10.2 发布端目标

1. 辅导员、学院、社团或组织身份管理；
2. 结构化通知编辑器；
3. 适用人群、条件、任务、日期、材料和证据配置；
4. 从自然语言通知自动生成结构化草稿并人工确认；
5. 生成小程序卡片、二维码或分享入口；
6. 发布、延期、修改、撤销与版本记录；
7. 只展示聚合完成情况，不默认暴露学生敏感信息；
8. 通知模板库与常见错误检查；
9. 发布前预览不同身份用户将看到的行动路径。

### 10.3 AI 服务目标

AI 流水线固定为：

```text
输入接收
→ OCR/版面解析
→ 文档清洗与分段
→ 候选事实抽取
→ 用户与适用对象匹配
→ Action Graph 构建
→ 时间/条件/材料规则校验
→ 字段级证据对齐
→ 严重错误风险复核
→ 置信校准与拒答
→ Verified Action Object
→ 用户确认与任务落库
```

模型不得直接控制提醒发送、任务完成或外部提交。所有有副作用的动作必须经过用户明确确认。

### 10.4 后端与运营目标

- 文档、行动、证据、任务、通知版本和用户反馈可追踪；
- 模型版本、Prompt 版本、规则版本和请求 ID 可审计；
- 密钥只保存在服务端；
- 支持速率限制、失败重试、熔断、缓存和降级；
- 解析失败时保留原文和人工建任务能力；
- 提供匿名化质量仪表盘；
- 所有关键数据提供删除机制；
- 正式环境与演示环境隔离；
- 提供数据库备份、恢复和异常告警。

## 11. 程序验收标准

### 11.1 P0：可参赛完整度

- 从导入通知到保存任务的全链路可用；
- 学生端、发布端和管理端都能在正式环境运行；
- 至少支持文本、截图和 PDF 三种输入；
- 不依赖开发者手工修改数据库完成演示；
- 无网络、模型超时、OCR 失败均有明确降级；
- 隐私政策、用户协议、数据删除和权限说明完整；
- 连续 100 次核心链路测试无崩溃。

### 11.2 P1：冲击 2 万至 3 万元档

- 达到实验最低通过线；
- 完成 CampusActionBench 冻结测试；
- 至少一个真实组织、30 名真实用户试点；
- 复杂通知演示稳定；
- 关键结论均能定位证据；
- 不确定日期不会被自动补成确定时间。

### 11.3 P2：冲击一等奖

- 达到“冲一等奖目标”指标；
- 至少 3 个独立组织、100 名用户、14 天真实试点；
- 学生端与发布端形成双向闭环；
- 有通知变更自动同步和任务版本追踪；
- 能提供通用模型对照、消融、鲁棒性和用户实验；
- 答辩中的用户、通知和统计数据均可追溯；
- 形成 20 秒核心演示、3 分钟标准答辩和无网备用演示。

---

## 12. 冻结改进建议

### 12.1 最高优先级：从 Action List 升级为 Action Graph

不能把所有通知压成一张静态卡。必须表达：多个行动、执行顺序、条件分支、不同人群、附件依赖、延期和撤销。复杂通知是与通用模型拉开差距的主战场。

### 12.2 把“可信性”设计成可见功能

证据不能只存在后台。用户点击截止时间、材料和后果时，应立即看到原文高亮；“明确、推断、估计、未知”应有不同视觉状态。系统的克制必须能被用户和评委看见。

### 12.3 建立 Critical Error Shield

对相关性、截止时间、材料和提交渠道进行独立复核。若抽取结果和证据不一致、时间表达存在歧义或多个模型结论冲突，系统必须进入“需要确认”，不得追求表面上的全自动化。

### 12.4 增加发布端，形成网络效应

只有学生端时，产品容易被看作个人效率工具。加入发布端后，教师可以确认结构化任务，学生获得零歧义信息，修改能够同步，产品由“工具”升级为“校园行动协议”。

### 12.5 让微信成为产品机制的一部分

微信价值必须体现在分享入口、小程序卡片、扫码即用、群聊场景、订阅消息和组织触达，而不是仅把 Web 产品装进小程序容器。

### 12.6 用真实部署替代商业想象

当前阶段不重点讲医疗、银行和政务扩展。答辩优先展示真实学院、班级、社团或实验室使用数据，以及任务完成率和发布者节省时间。

### 12.7 建立“模型失败也是结果”的机制

系统要保存拒答、超时、冲突和用户纠正，建立错误案例库。优秀 AI 项目不是声称“准确率 100%”，而是知道何时不能自信回答，并能把风险安全地交给用户。

### 12.8 首页坚持任务中枢设计

首页默认展示“今天要做、即将截止、等待前置、需要确认”，导入通知作为核心入口；AI 对话只能作为辅助解释器，不得成为首页主体。

## 13. 固定核心演示用例

演示通知必须同时包含：

- 两类以上适用对象；
- 至少一个排除条件；
- 三个以上行动；
- 两个不同截止时间；
- 在线和线下两个渠道；
- 三份以上材料；
- 一个前置依赖；
- 一个含糊或冲突字段；
- 一条后续延期/变更通知。

演示画像固定为“符合部分条件但不符合全部默认条件的本科生”，以展示个性化裁剪。

演示流程固定为：

1. 导入长截图或 PDF；
2. 系统判断是否相关；
3. 生成 Action Graph；
4. 点击关键字段查看证据；
5. 对含糊日期触发确认；
6. 保存任务并设置提醒；
7. 导入延期通知；
8. 原任务自动更新并保留变更记录。

## 14. 里程碑与停止条件

### M1：协议与数据冻结

完成 Action Object schema、标注指南、800 条数据计划、基线定义和测试集冻结工具。

### M2：端到端工程闭环

文本/截图/PDF能够生成有证据的行动并保存为任务；学生端核心页面可用。

### M3：可信系统闭环

Action Graph、身份匹配、证据定位、时间规则和严重错误盾上线；完成验证集调优。

### M4：真实试点与送审

发布端上线，至少一个组织开始使用；完成隐私、类目、域名、权限和小程序审核材料。

### M5：正式冻结评测

锁定代码、模型、Prompt、规则和环境；执行一次正式测试；生成不可覆盖的结果、日志和哈希。

### M6：一等奖答辩包

完成试点数据、实验报告、答辩 PPT、3 分钟脚本、演示视频、在线演示和离线备用演示。

### 停止/降级条件

若正式提报前无法稳定实现复杂通知、证据定位和任务闭环，则停止增加发布端高级功能与扩展场景，集中确保 P0 完整度。若真实试点规模未达到一等奖线，必须如实降级为初步试点，不得夸大。

## 16. 冻结裁决

本项目正式冻结为：

> **Campus Action OS：以 Verified Action Object、Action Graph、字段级证据、严重错误盾和双向校园发布协议为核心的可信校园行动操作系统。**

正式实验以 CampusActionBench 的 Critical Error Rate 与 Action Recall 为共同主要终点；正式产品以学生端行动闭环、发布端结构化通知闭环和真实校园试点为一等奖级验收条件。

此后所有新增功能必须回答两个问题：

1. 是否显著提升实用性、创新性、用户体验或完整度？
2. 是否能产生可验证的证据，而不是只增加演示复杂度？

若两个问题均为否，则不进入正式版本。
